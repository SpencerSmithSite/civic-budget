# Walkthrough 28: SOC 2 by design

A government that buys software asks for a SOC 2 report. An ERP vendor reselling CivicBudget
will ask for one before its own customers do. A SOC 2 report is an independent CPA's opinion
that a service's controls are designed well (Type 1) and that they worked over months (Type 2).
I have not hired an auditor yet. I built what the auditor examines, mapped each
control to its evidence, and wrote the policies an operator would follow. The wording everywhere
is "designed and built to achieve SOC 2 compliance", which is true, and not "SOC 2 compliant",
which needs the report.

This phase added the missing controls, then the paperwork:

1. a security log;
2. sessions that end;
3. rate limits and security headers;
4. a government's data, in and out;
5. scanning in CI;
6. the documents (`docs/security`).

## 1. A security log, apart from the audit trail

The audit trail (walkthrough 3) records every change to a budget: who, when, the old value, the
new value. An auditor also asks "who got in, who tried to, and what left the building". Putting
sign-ins in the audit trail would bury the budget history under hundreds of sign-in rows, so the
answer is a second table, `SecurityEvent`.

| Recorded | Where it is written |
|---|---|
| Signed in, wrong password, unknown address, locked out, asked for a code, wrong code, recovery code used, signed out | `AuditingSignInManager`, which overrides Identity's `SignInManager` |
| Signed out after 30 idle minutes | the same override, told by `/Account/SessionExpired` through `HttpContext.Items` |
| Password changed | the change-password page and the reset link |
| Exported (every file) | one endpoint filter on the `/admin/export` group |
| Too many attempts | the rate limiter's `OnRejected` |
| Government removed, old records removed | the operator's commands |

Two choices in that table are worth explaining.

**Overriding the sign-in manager.** Every sign-in path (the login page, the two-step page, the
recovery code page, and any added later) calls the sign-in manager. Logging in the override means
nobody has to remember to log in a page.

**Unknown addresses belong to nobody.** The overload that takes an email looks the person up first.
If there is no account, it records `UnknownAccount` with no government and returns the same
failure as a wrong password, so the page still cannot be used to find out who has an account.
Those events are the operator's, for spotting someone trying a list of addresses.

The events are not tenant-filtered, because some have no government. `SecurityLogService` scopes by
the signed-in Administrator's government itself, as the Identity services do (ADR-0015). A failure
to write the row is logged and swallowed: a sign-in is never refused because its log row could not
be saved.

Administrators read it on **Security log**, filtered by kind, 50 at a time.

## 2. Sessions that end

The rules:
- **30 minutes** without activity signs you out;
- **14 days** if you ticked "Remember me".

The server half is Identity's cookie: `ExpireTimeSpan` of 30 minutes, sliding, and
`OnSigningIn` sets 14 days when the sign-in is persistent. That alone is not enough for a Blazor
app. Once the worksheet is open, the browser talks to the server over the circuit's WebSocket, and
the cookie is never sent again. The server cannot tell an idle tab from a busy one.

So the browser keeps its own clock (`wwwroot/js/session.js`):

- The page says how long a session lasts on `<body data-idle-minutes="30">`. The attribute is left
  off for a remembered device, so the script does nothing there.
- Keys, clicks, scrolling, and touches count as activity, shared across tabs through
  `localStorage`. Working in one tab keeps the others alive.
- While someone is active, a quiet request to `/Account/KeepAlive` every five minutes slides the
  cookie.
- Two minutes before the limit, a banner counts down with a **Stay signed in** button.
- At the limit, the page goes to `/Account/SessionExpired`. That endpoint signs out, records
  "Signed out, idle", and shows the sign-in page with "You were signed out after 30 minutes
  without activity."

Deactivating someone, changing their role, or resetting their password changes their security
stamp. Both the cookie and each open page now re-check the stamp every 5 minutes, down from
Identity's 30 (`SessionPolicy.RecheckEvery`), so a person who leaves loses access within 5 minutes.

## 3. Rate limits and headers

**Rate limits** use ASP.NET Core's built-in limiter.

| Request | Limit |
|---|---|
| Sign in, second step, recovery code (POST) | 20 per 5 minutes per address |
| Forgot password, reset password (POST) | 5 per 15 minutes per address |
| Exports | 60 per minute per signed-in user |
| Everything else | none |

Lockout already stops guessing one account's password. The limits stop one address trying many
accounts, or flooding the reset form. `RateLimits.PolicyFor(HttpContext)` decides which rule
applies. It is a pure function, so the table above is a unit test. The address comes from
`X-Forwarded-For`, and only the entry Azure's load balancer added is trusted, so a client cannot
pick its own partition.

**Headers** come from `SecurityHeadersMiddleware`, on every response including output cache hits:

```
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-…'; style-src 'self' 'unsafe-inline';
  img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; object-src 'none';
  base-uri 'self'; form-action 'self'; frame-ancestors 'none'
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
```

Scripts may come only from this site, which is what blocks injected script. Two inline scripts
stood in the way:
- the small `window.civicBudget` helpers moved to `js/civicbudget.js`;
- Blazor's import map has to be inline, so it carries a nonce: a random value made per request,
  put on the tag and in the header, which an attacker cannot guess.

(*Since 2026-10-02:* a third, the waiting screen's script, was missed here and blocked by the
policy; it is now `js/waiting.js`.)

Two more details:
- **Blazor's own header.** Blazor adds `frame-ancestors 'self'` on its own. My middleware keeps any
  policy already set (an uploaded image carries a stricter sandbox policy), so Blazor's header
  would have won. `Program.cs` switches it off.
- **Inline styles are still allowed.** The report bars set their widths inline. The risk the policy
  exists for is script.

I checked it by opening every page as every demo user with the role sweep: no policy violations in
the console.

## 4. A government's data, in and out

Two questions come up in every security review:
- "Can we get all our data out?"
- "What happens to it when we leave?"

Both are answered by `GovernmentDataStore`, which finds a government's data from the EF model
rather than from a list. Its scope:

- every table with a `GovernmentId` column;
- the `Governments` row itself;
- tables without one that point at one of those, such as a user's roles and department links,
  reached through the foreign key.

A table added next year is covered the day it is added. A test compares the covered tables with
every table in the model and fails on one that no government reaches. The only exceptions are
three shared on purpose: the role names, their claims, and the Data Protection keys.

**Download everything** (Government settings, Administrators only) writes a ZIP:
- one CSV per table, with a README listing the files and row counts;
- withheld: password hashes, security stamps, two-step keys and recovery codes, and images;
- text starting with `=`, `+`, `-`, or `@` gets an apostrophe, so a spreadsheet shows a comment
  instead of running it as a formula.

**Leaving** is an operator command, like `--provision`:

```bash
dotnet run --project src/CivicBudget.Web -- --offboard --slug cedar-falls-oh --export-to ~/secure/cedar-falls.zip --confirm cedar-falls-oh
```

It refuses without the slug typed twice, and refuses to overwrite a file. It writes the export
first and deletes nothing if that fails. Then it deletes in one transaction.

The order matters. Many foreign keys do not cascade (SQL Server refuses multiple cascade paths), so
each table must be deleted before the tables it points at. `DeletionOrder` takes, at each step, a
table no remaining table points at: budget lines before budget versions, before fiscal years,
before the government. A version that points at the version replacing it is fine, because one
statement removes both. The security log is kept for the rest of its year as the operator's
evidence.

**Retention**: `--maintenance`, run daily by the platform's scheduler, removes security events and
finished emails older than a year. It never removes an email still waiting to be sent. It is a
command rather than a timer in the app, for the same reason the email sender does not poll:
anything that wakes the database on a schedule keeps the free demo database from pausing
(walkthrough 18).

## 5. Scanning in CI

| Check | When |
|---|---|
| `NuGetAudit` in `Directory.Build.props`: every package, including ones pulled in by others, against the GitHub advisory database. With warnings as errors, a known vulnerability of any severity fails `dotnet restore`, locally and in CI. | Every build |
| `security.yml`: CodeQL with the `security-extended` queries, for C# and the browser scripts | Every change and every Monday |
| `security.yml`: the package check | Every change and every Monday |
| Dependabot: NuGet, GitHub Actions, and the npm scripts | Weekly |

The weekly run matters: an advisory published on Tuesday for a package that has not changed
would otherwise wait for the next push. The CodeQL action is pinned by commit, like the others.

## 6. The documents

`docs/security/` is what a buyer's security questionnaire, or an auditor, reads first:

- **README**: what SOC 2 is, what "designed to achieve" means, who is responsible for what
  (the software, the operator, each government, the host), the controls in brief, other frameworks,
  and the known gaps.
- **control-matrix.md**: every SOC 2 criterion in scope, what meets it, where it lives in the
  code, the evidence, and the NIST CSF 2.0 and NIST 800-53 references (the catalog GovRAMP uses).
- **policies/**, written for the operator: information security, access control, change
  management, vulnerability management, secure development, incident response, business continuity
  and backups (RPO 15 minutes, RTO 4 hours), data retention and disposal, and vendor management.
- **SECURITY.md** at the root: how to report a vulnerability.

CJIS, IRS 1075, and HIPAA are named and ruled out: no criminal justice information, no federal
tax information, no health information.

## 7. Tests

- **Integration** (`SecurityTests`, against SQL Server):
  - each sign-in outcome writes its event, and an unknown address belongs to no government;
  - five wrong passwords lock the account, and the log says so;
  - only an Administrator reads the log, and only their own government's;
  - the full export has every table of one government and no secrets, and matches the database's
    row counts;
  - every table is reached from a government unless shared on purpose;
  - removing a government deletes every row it had (checked against the database catalog, not the
    code under test) and leaves the other government exactly as it was;
  - retention removes year-old records but never a waiting email.
- **Web** (`SecurityControlsTests`):
  - which requests are limited;
  - the session lengths, cookie flags, and the 5-minute re-check;
  - the headers, the nonce, and that a stricter policy already set is kept;
  - the Security log page, in the grid and on phones.
- **In a browser**:
  - the role sweep with no policy violations;
  - the download;
  - the log;
  - the warning at 28 minutes and the sign-out at 30, using Playwright's fake clock;
  - 5 password resets from one address, then 429 for the rest.
